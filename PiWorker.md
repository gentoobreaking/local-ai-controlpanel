 技術上可行，但會破壞現有安全架構

 ### 目前架構：零網路 Worker

 ```
PiAgentWorker (無網路)
    │
    ├─ read_file / write / edit  → 本地檔案系統 (受 workspaceRoot 限制)
    └─ web_search                → 呼叫注入的函式 → Control Plane (有網路)
                                    │
                                    ▼
                         ┌─────────────────────┐
                         │ Web Retriever       │
                         │ MCP Servers         │
                         │ 瀏覽器自動化        │
                         └─────────────────────┘
 ```

 ### 若要給 Worker 直接網路權限，需修改三處

 ┌─────────────┬──────────────────────────────┬──────────────────────────────────────────────────────────┐
 │ 修改點      │ 現狀                         │ 改成有網路後                                             │
 ├─────────────┼──────────────────────────────┼──────────────────────────────────────────────────────────┤

 ├─────────────┼──────────────────────────────┼──────────────────────────────────────────────────────────┤

 ├─────────────┼──────────────────────────────┼──────────────────────────────────────────────────────────┤

 └─────────────┴──────────────────────────────┴──────────────────────────────────────────────────────────┘

 ### 具體改法範例

 ```typescript
// 1. 新增網路工具
tools.push({
  name: "http_request",
  label: "HTTP Request",
  description: "發送 HTTP 請求 (僅限允許域名)",
  parameters: Type.Object({
    method: Type.String({ enum: ["GET", "POST"] }),
    url: Type.String({ format: "uri" }),
    headers: Type.Optional(Type.Record(Type.String())),
    body: Type.Optional(Type.String()),
  }),
  execute: async (_id, { method, url, headers, body }) => {
    // 新增：域名白名單檢查
    if (!isUrlAllowed(url)) {
      return { content: [{ type: "text", text: `(denied: domain not allowed)` }] };
    }
    const resp = await fetch(url, { method, headers, body });
    const text = await resp.text();
    return { content: [{ type: "text", text: text.slice(0, 50_000) }] };
  },
});

// 2. 域名白名單 (配置化)
const ALLOWED_DOMAINS = new Set([
  "api.github.com",
  "registry.npmjs.org",
  "pypi.org",
  "docs.python.org",
  // ...
]);

function isUrlAllowed(url: string): boolean {
  try {
    const u = new URL(url);
    return ALLOWED_DOMAINS.has(u.hostname);
  } catch { return false; }
}
 ```

 ┌──────────────┬─────────────────────────────────────────────────────────┬───────────────────────────────────────┐

 └──────────────┴─────────────────────────────────────────────────────────┴───────────────────────────────────────┘

 ### 何時會考慮給 Worker 網路？

 1. 離線優先環境：Worker 跑在無法連 Control Plane 的隔離網段
 2. 極低延遲需求：不想經過 Control Plane 轉發 (但通常網路 I/O 不是瓶頸)
 3. 特殊協議：需直接呼叫非 HTTP 協議 (如 WebSocket、gRPC、原始 TCP)

 ### 建議

 ▏ 維持現狀：Control Plane 統一網路出口，Worker 零網路。
 ▏
 ▏ 若真有「Worker 需直連」的剛需，建議：
 ▏ 1. 先評估能否用現有 webSearch + MCP Server 解決
 ▏ 2. 若必須直連，建立 NetworkCapableWorker 子類別，明確標記有網路權限，並強制要求沙箱執行 (seatbelt/bwrap --unshare-net
 ▏    + 域名白名單)
 ▏ 3. 不要把網路能力混入基礎 PiAgentWorker，保持基類乾淨

 結論：能改，但強烈不建議改基礎架構。現有「注入函式」模式已足夠表達所有搜尋/檢索需求，且安全性、可測試性、策略集中化都更
 優。

 ### 6. 防禦深度：現有架構的多層防護

 ```
Layer 1: Worker 零網路 (物理隔離)
    └─ 即使模型產生任意 URL，工具不存在，根本呼叫不了

Layer 2: Control Plane 注入函式 (邏輯隔離)
    └─ webSearch(query) 只回傳「搜尋結果」，不暴露 HTTP 客戶端

Layer 3: Web Retriever / MCP Server (執行隔離)
    ├─ 獨立進程/容器，有獨立網路命名空間
    ├─ 域名白名單、速率限制、請求審計
    └─ 回應經過清洗 (移除敏感標頭、截斷大小)

Layer 4: 沙箱 (seatbelt/bwrap --unshare-net)
    ├─ 即使 Worker 被逃逸，也無網路命名空間
    └─ 檔案系統只見 workspaceRoot
 ```

 ### 7. 若必須直連，最低安全基線

 ```typescript
// 僅作為架構討論參考，不建議實作
interface NetworkPolicy {
  // 1. 域名白名單 (嚴格)
  allowedDomains: string[];           // 如 ["api.github.com", "registry.npmjs.org"]
  allowedCIDRs?: string[];            // 禁用私有 IP 段

  // 2. 協議限制
  allowedProtocols: ["https"];        // 禁用 http、ftp、ws、tcp

  // 3. 請求限制
  maxRequestSize: 1024 * 1024;        // 1MB
  maxResponseSize: 10 * 1024 * 1024;  // 10MB
  timeoutMs: 10_000;
  maxRedirects: 0;                    // 禁用重導向 (防 SSRF)

  // 4. 標頭管控
  forbiddenRequestHeaders: ["authorization", "cookie", "x-api-key"];
  stripResponseHeaders: ["set-cookie", "server", "x-powered-by"];

  // 5. 審計
  auditLog: (req, resp) => void;      // 全量記錄

  // 6. 執行環境
  requireSandbox: true;               // 必須在 --unshare-net 沙箱內
  networkNamespace: "isolated";       // 獨立網路命名空間
}
 ```

 ### 結論

 ▏ 給 Worker 直連網路 = 打開潘朵拉盒子
 ▏
 ▏ - 目前「零網路 + 注入函式」架構將網路風險集中在 Control Plane，單一出口易防禦、易審計、易升級
 ▏ - 分散到每個 Worker 變成 N 個出口，每個都要完美實作白名單、速率限制、審計、沙箱隔離，一處疏漏全盤皆輸
 ▏ - LLM 的非確定性 + Prompt Injection 特性，讓「事前防禦」極其困難，事後審計才是可行防線

 建議：維持現架構。若有特殊場景需直連，請建立獨立的 NetworkCapableWorker 子類，強制要求沙箱 + 獨立網路命名空間 +
 完整審計，且不修改基礎 PiAgentWorker。
